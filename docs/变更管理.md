# 变更管理

项目演进通过四类文档跟踪，各管一件事，不重复记录：

| 文档 | 回答的问题 | 何时写 |
| --- | --- | --- |
| [`CHANGELOG.md`](../CHANGELOG.md) | 每个版本改了什么 | 每个对外可感知的改动，合入时追加到「未发布」 |
| [`docs/adr/`](./adr/README.md) | 架构为什么这样定 | 做出影响模块边界、数据结构、对外接口或技术选型的决策时 |
| [`docs/架构设计.md`](./架构设计.md) | 现在是什么样 | 架构变化后同步更新，只描述当前状态 |
| `docs/方案/` | 某个子系统具体怎么设计和实现 | 实现复杂、需要说明安全模型、测试策略或维护约定的子系统；随实现同步更新 |

四者的关系：
- ADR 记录决策和理由，CHANGELOG 记录决策落地后的结果。
- 架构设计文档始终反映最新状态。
- 方案文档展开单个子系统的细节，由架构设计文档链接过去。

## 模块标签

每条 changelog 条目、每次提交的 scope 都使用下表的标签，按标签就能追溯单个模块的完整演进。

| 标签 | 范围 | 代码位置 |
| --- | --- | --- |
| `server` | 应用组装、启动命令、运行配置 | `backend/src/kb_studio/{apps,cli.py,settings.py}` |
| `api-public` | 问答端接口契约（路径、参数、SSE 事件） | `backend/src/kb_studio/api/public/` |
| `api-admin` | 管理端接口契约 | `backend/src/kb_studio/api/admin/` |
| `auth` | 管理员密码、token、接口鉴权 | `backend/src/kb_studio/auth.py` |
| `ingest` | 增量入库、文档版本、索引版本与重建 | `backend/src/kb_studio/ingest/` |
| `eval` | 回归测试执行与判定 | `backend/src/kb_studio/evaluation/` |
| `query` | 只读查询：当前索引解析、检索、生成 | `backend/src/kb_studio/query/` |
| `rag` | 模型工厂、切分、向量库客户端、Prompt | `backend/src/kb_studio/rag/` |
| `db` | 表结构、数据迁移、repo | `backend/src/kb_studio/db/` |
| `storage` | 原文件存储 | `backend/src/kb_studio/storage/` |
| `web-shared` | 前端共享层：HTTP 客户端、外壳、应用地址、主题、通用工具 | `frontend/src/shared/` |
| `web-chat` | 问答应用与暗门 | `frontend/src/apps/chat/`、`index.html` |
| `web-admin` | 管理应用：登录与后台页面 | `frontend/src/apps/admin/`、`admin.html` |
| `build` | 依赖、构建配置、检查脚本 | `pyproject.toml`、`package.json`、`scripts/`、配置文件 |
| `docs` | 文档与 AI 规则 | `docs/`、`README.md`、`AGENTS.md` |

新增模块时先在这里登记标签，再开始使用。

## CHANGELOG 书写规范

- 格式遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，分类为：新增、变更、弃用、移除、修复、安全。
- 每条以模块标签开头：``- `ingest` 同名文件内容未变时跳过入库``。跨模块的改动列出主要模块，用 `/` 分隔。
- **写结果，不写过程**：一条一句话，说明行为或能力的变化，不描述实现步骤和排查过程。
- **关键细节要写清楚**：以下情况要补充必要的细节，可以用缩进的子条目：
  - 数据结构或块 ID 规则变化
  - 需要重建索引、迁移数据或重新登录
  - 接口不兼容（在条目前标注 **破坏性**）
  - 有安全影响的改动
- 发布前修掉的问题不记录，只记录相对上一个已发布版本的差异。
- 只改测试、重构且行为不变的改动不进 changelog，在提交记录里体现即可。

## 版本号

遵循 [语义化版本](https://semver.org/lang/zh-CN/)。`1.0.0` 之前：

| 改动 | 版本位 |
| --- | --- |
| 接口不兼容、数据结构变化需要迁移或重建 | 次版本号，`0.x.0` |
| 新增功能、行为调整、修复 | 修订号，`0.x.y` |

版本号同时维护在 `backend/pyproject.toml` 和 `frontend/package.json` 中，两处保持一致。

## 发版流程

分支模型见 [开发规范 · Git 工作流](./开发规范.md#git-工作流)：日常开发在 `develop`，`main` 只保存已发布版本。

1. 在 `develop` 上把「未发布」下的条目归入新版本，标题写成 `## [x.y.z] - YYYY-MM-DD`。
2. 同步更新 `backend/pyproject.toml` 和 `frontend/package.json` 的版本号。
3. 检查 `docs/架构设计.md` 是否反映了本版本的架构变化，并运行 `scripts/check.sh`。
4. 在 `develop` 上提交：`chore(build): 发布 x.y.z`。
5. 合并到 `main` 并打 tag：

   ```bash
   git switch main
   git merge --no-ff develop -m "chore(build): 合并 develop，发布 x.y.z"
   git tag -a vx.y.z -m "x.y.z"
   git switch develop
   ```

## 提交规范

使用 Conventional Commits：`type(scope): 中文描述`，scope 取上面的模块标签。

```
feat(ingest): 同名文件内容未变时跳过入库
fix(web-chat): 输入法组字时回车不再触发发送
refactor(query): 检索参数改由调用方传入
docs(adr): 新增 0007 混合检索
```

按模块查看演进：

```bash
grep '`ingest`' CHANGELOG.md          # 版本维度
git log --oneline --grep='(ingest)'   # 提交维度
```
