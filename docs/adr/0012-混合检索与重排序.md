# 0012 混合检索与重排序

- 状态：提议中
- 日期：2026-10-23
- 涉及模块：`query` `rag` `ingest` `eval` `db`
- 方案文档：[检索质量](../方案/检索质量.md)

## 背景

当前只有单路向量检索加相关度门槛（ADR 0005）。对制度编号、错误码、专有名词这类问题召回差，相关片段也可能因为排在 top_k 之后被截断。同时缺少检索层面的指标，任何检索改动都无法量化收益。

## 决策

**先度量**

- 回归用例增加 `expected_doc_ids`。
- 报告给出 Hit@K、Recall@K、MRR、候选 Recall、误召回率和各阶段耗时。
- 评测集扩充到 50 条以上并记录基线后，才开始修改检索链路。

**混合检索**

- 关键词检索使用 SQLite FTS5 + jieba 预分词，`bm25()` 排序，标题列加权。
- 每个索引版本对应一个关键词索引文件 `data/lexical/<collection>.db`，属于派生数据，随 collection 一起创建和删除。
- 分词配置（词典哈希、规则版本）随索引版本固化。
- 两路召回结果用 RRF 融合，只使用排名，不使用原始分数。

**相关度门槛**

- 对融合后的全部候选，统一用“问题与片段的余弦相关度”和原有的 `score_threshold` 判断。片段向量从向量库读取，不额外调用 Embedding。
- ADR 0005 的拒答语义保持不变。

**重排序**

- 定义 `Reranker` 接口，首期实现百炼文本排序 API。
- 只对通过门槛的候选排序；超时或失败时按融合顺序继续，不中断问答。
- 重排序分数门槛默认不设置，用评测集校准后再启用。

**问题改写**

- 默认只在有对话历史时改写，改写结果只用于检索，生成阶段仍使用原问题。
- 超时或输出不合法时使用原问题。

**发布方式**

- 所有新步骤都是运行参数，可以单独开关，不需要重建索引。
- 后台提供“试运行”：用候选参数跑一遍回归测试，与当前参数对比后再保存。
- 升级后默认保持 `vector` 模式。

## 备选方案

- **内存 BM25（rank_bm25）**：每个进程一份，启动时全量加载，变化后要整体重算，不适合多进程部署，排除。
- **FTS5 trigram 分词**：两个字的中文词查不到，排除。
- **Elasticsearch / OpenSearch**：效果和扩展性最好，但需要独立集群，违背本地优先的定位，留给服务端部署再评估。
- **分数加权融合**：向量分数和 BM25 分数尺度不同，权重需要按数据调参且不稳定，排除。
- **本地重排序模型**：不外发数据，但在 CPU 上延迟过高，还会引入 torch 等重依赖，作为数据不允许外发时的替代实现。
- **门槛只作用于向量召回的结果**：只来自关键词的偶然命中会绕过门槛，误召回率上升，排除。

## 影响

- `index_versions` 增加 `lexical_tokenizer`。已有版本为空，检索时自动退回 `vector` 模式，可以“补建关键词索引”，补建不调用 Embedding。
- `eval_cases` 增加 `expected_doc_ids`。
- 新增依赖 `jieba`。
- 新增派生数据目录 `data/lexical/`，删除后可以补建。
- 启用重排序后，首字延迟预计增加 0.5–1 秒；预算见方案第 14 节。
- 规划中阶段 4 的 Recall@K 提前到阶段 3 实施。
