# 0007 应用边界与可拆分部署

- 状态：已采纳
- 日期：2026-10-21
- 涉及模块：`server` `api-public` `api-admin` `query` `web-shared` `web-chat` `web-admin`

## 背景

问答和管理原本在同一个 FastAPI 应用、同一个前端 SPA 里，只靠路由前缀和前端路由区分。这样的结构没法单独部署：管理接口没法只在内网暴露，查询链路和入库链路也没法分开扩容。随着代码增长，两侧的代码还会越来越难拆开。

## 决策

**应用拆分**

- 后端拆成 `chat_app`（:8765，只读）和 `admin_app`（:8766，读写加鉴权）两个应用，各自只托管自己的前端入口页。
- 前端改为多页构建：`index.html` 对应 `src/apps/chat`，`admin.html` 对应 `src/apps/admin`，公共代码放在 `src/shared`。
- 两个应用之间只通过 URL 跳转。暗门只负责跳转，登录页属于管理应用。

**只读查询层**

- 新增 `kb_studio.query` 作为只读查询层，问答端和回归测试共用同一条查询链路。

**边界检查**

- 用工具强制检查边界：后端用 import-linter（分层、问答端只读、两个应用独立），前端用 ESLint `no-restricted-imports`（应用互斥、共享层不依赖应用、禁止 `../`）。

**运行与配置**

- 默认用 `kb-studio` 在同一进程中启动两个应用，共享本地 Chroma 客户端；分进程部署时必须改用 Chroma 服务端（`KB_CHROMA_URL`）。
- 部署相关配置全部改为环境变量（`KB_*`、`VITE_*`）。

## 备选方案

- **立即拆成 monorepo 和两个仓库**：边界最彻底，但对单人本地使用来说维护成本过高。当前的目录结构可以直接平移成 `apps/chat`、`apps/admin`、`packages/shared`。
- **只做逻辑分层，不拆端口**：代码约束到位了，但网络层面无法隔离，管理接口仍然和问答一起暴露。

## 影响

- **破坏性**：后台地址从 `:8765/#/admin` 改为 `:8766`；后端入口从 `kb_studio.main` 改为 `kb_studio.cli`。
- 物理拆分的触发条件：
  - 出现多个用户或多种角色
  - 后台需要只在内网开放
  - 入库任务开始影响问答延迟
  - 需要单独发布其中一个应用
- 物理拆分时的后续工作：
  - 前端改为 pnpm workspace
  - 后端把 `ingest` 改为独立 Worker，并接入任务队列
  - 数据层改为服务端数据库与向量库，分别配置只读、读写权限
- 两个应用目前共享同一份数据，数据层的权限隔离留到迁移服务端存储时再做。
