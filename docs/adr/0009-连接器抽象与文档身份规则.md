# 0009 连接器抽象与文档身份规则

- 状态：已采纳
- 日期：2026-10-23
- 涉及模块：`ingest` `db` `storage` `query` `api-admin` `api-public`
- 方案文档：[多数据源接入](../方案/多数据源接入.md)

## 背景

知识目前只能通过后台手动上传 `.md` / `.txt` 进入系统，文档用文件名识别（ADR 0003）。要从飞书等企业文档平台同步知识，需要回答三个问题：

- 不同来源怎么接入同一条入库链路。
- 外部文档怎么识别为“同一篇”：标题可以改、可以重名，文件名不再可靠。
- 外部文档的增删改怎么反映到索引里，而且不能因为一次异常同步把知识库清空。

## 决策

**连接器抽象**

- 每种来源实现一个连接器：`list_documents()` 返回轻量的文档清单（ID、标题、链接、源端更新时间），`fetch(ref)` 返回原始内容。
- 手动上传也作为一种来源（`upload`），走推送模式，复用同一套入库函数，不实现 `list_documents`。
- 同步引擎与连接器分离：引擎负责对比、入库、删除和记录，连接器只负责“列出”和“取回”。

**文档身份**

- 文档身份由文件名改为 `(data_source_id, source_id)`：
  - `source_id` 是源系统里的稳定 ID，比如飞书节点 token、本地目录的相对路径。
  - 手动上传的 `source_id` 仍是文件名，现有行为不变。
- `documents.filename` 改为 `title`，只用于展示，不再唯一。
- 内部 `doc_id` 和块 ID `{doc_id}:{序号}` 不变，ADR 0003 中的块替换规则继续适用。

**两级变化判断**

1. 源端更新时间没变：不取回内容。
2. 取回后，对解析出的 Markdown 文本计算 SHA-256；哈希没变就不重新向量化。

对 `.md` / `.txt`，解析结果就是原文，哈希与现有数据一致，迁移后不会触发重复入库。

**原文与解析结果分开保存**

- `raw` 保存源端原始内容，比如飞书 blocks JSON、上传的原文件。
- `parsed.md` 保存解析结果，入库和全量重建都读这个文件。

**删除保护**

- 只有完整列举成功时才处理“源端已删除”。
- 本次待删除的文档数超过该来源现有文档数的 50% 时，中止删除并报警，等人工确认。

**同步来源的文档在后台只读**

- 不能手动删除或回退，否则下次同步会覆盖。
- 要排除文档，在数据源配置里调整范围。

## 备选方案

- **用标题或路径作为身份**：飞书文档改名、移动后会被当成新文档，旧文档残留，排除。
- **对原始内容计算哈希**：飞书 blocks JSON 里包含与正文无关的字段（如修订号），会产生大量无效的重新向量化，排除。
- **每个来源一个 collection**：检索时要合并多个 collection 的结果并重新排序，还会打破“一个索引版本对应一个 collection”的蓝绿切换模型（ADR 0002），排除。
- **按“源端是否还存在”无条件删除**：接口异常、授权失效时，列表会返回空或残缺，可能误删整个知识库，所以加了完整性和比例两道保护。

## 影响

- 数据库需要迁移：重建 `documents` 表，新增 `data_sources`、`sync_runs` 表，引入 `PRAGMA user_version` 管理表结构版本；迁移前自动备份 `app.db`。
- 不需要重建索引：块元数据保持不变，来源链接在检索时按 `doc_id` 从元数据库补齐。
- **破坏性** 管理端接口 `filename` 字段改名为 `title`。
- ADR 0003 中“用文件名识别同一文档”的规则只对手动上传来源仍然成立；该 ADR 本身不修改，以本 ADR 为准。
