# 0015 会话服务与独立数据库

- 状态：提议中
- 日期：2026-10-23
- 涉及模块：`conversation` `server` `api-public` `api-admin` `build`
- 方案文档：[会话服务](../方案/会话服务.md)

## 背景

阶段 4 要保存用户的对话和反馈。这类数据与知识库数据的所有者、增长速度、敏感度、可见范围、保留期限和备份策略都不同。如果和知识库数据放在同一个数据库，隐私边界只能靠代码约定维持，保留期限清理和备份恢复也会互相牵连。

## 决策

**独立存储**

- 对话、消息、反馈存放在独立的会话数据库中：本地为 `data/conversation.db`，服务端为独立的 Postgres 数据库 `kb_conversation`，使用独立账号。
- 与知识库数据库没有共享表和跨库外键。用户以 `<provider>:<subject>` 形式的 `user_key` 引用；文档、索引、回归用例的引用都以不透明值保存。

**独立服务**

- 会话服务是唯一可以访问会话数据库的组件，对外提供版本化的内部接口 `/internal/v1`。
- 服务不理解知识库：不检索、不调用模型、不做文档权限校验。来源快照和检索追踪按不透明 JSON 保存，历史来源的权限由问答应用在读取后校验。
- 本地模式下，会话服务在同一进程内运行（`KB_CONVERSATION_MODE=embedded`）。服务端作为独立进程 `kb-studio-conversation` 部署（`remote`），只在内网监听。

**授权与隐私**

- 每个调用方使用独立的服务令牌和权限范围：问答应用为 `chat`，管理应用只有 `feedback:read` 和 `feedback:write`，worker 为 `user:purge`。进程内模式经过同一套授权检查。
- 服务不提供浏览他人对话的接口，管理侧只能读取用户主动提交的反馈快照。
- 历史可见性由部署级策略 `KB_CONVERSATION_HISTORY` 决定：
  - `enabled`（默认）：用户本人可见历史。
  - `session_only`：只保存当前会话，短期保留。
  - `disabled`：不保存。
- 保留期限、用户删除、离职清理由服务执行。

**可用性**

- 会话服务故障时，问答降级为单轮且不保存，并提示用户，不阻塞回答。
- 消息使用 `request_id` 保证幂等，使用租约识别崩溃中断。

**代码边界**

- 服务代码放在 `kb_studio.conversation`，调用方 SDK 放在 `kb_studio.conversation_client`。
- import-linter 保证：`conversation` 除 `settings` 外不依赖任何知识库模块；`api`、`evaluation`、`ingest` 只能经由 `conversation_client` 访问会话数据。

## 备选方案

- **与知识库共用数据库、独立模块**：实现最简单，但隐私边界和数据生命周期只能靠约定保证，排除。
- **LangGraph Checkpointer**：存的是图状态快照，无法按用户查询、按期限清理，也无法表达“管理侧只能读反馈”，排除。
- **独立仓库、独立技术栈**：边界最彻底，但目前的维护成本过高；代码边界已经保证随时可以拆出去。
- **只做独立数据库、不做服务接口**：问答和管理应用直接连会话数据库，隐私规则仍然依赖每个调用方自觉遵守，排除。

## 影响

- 新增模块标签 `conversation`、新的应用入口 `kb-studio-conversation`（默认端口 8767）、新的数据文件 `data/conversation.db`，以及配置项 `KB_CONVERSATION_*`。
- 本地默认启动方式不变；`data/conversation.db` 首次启动时自动创建，已有的 `data/app.db` 不受影响。
- 服务端部署增加一个进程和一个数据库，备份策略单独制定。
- ADR 0013 中的会话存储由本 ADR 决定；ADR 0013 的分层契约中不再包含 `conversation`。
- import-linter 新增 4 条契约，与 ADR 0010、0013 一起修改 `backend/pyproject.toml`。
