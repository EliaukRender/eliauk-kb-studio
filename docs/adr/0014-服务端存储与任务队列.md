# 0014 服务端存储与任务队列

- 状态：提议中
- 日期：2026-10-23
- 涉及模块：`server` `db` `storage` `rag` `ingest` `eval` `build`
- 方案文档：[服务端部署](../方案/服务端部署.md)

## 背景

ADR 0001 把三层数据都放在本地：SQLite、本地 Chroma、`data/raw/`；后台任务使用进程内的 `BackgroundTasks`。这套组合不支持多实例共享数据，重启会中断任务，也没有并发控制。阶段 2 的权限过滤在这套存储上有容量上限（ADR 0011）。服务端部署需要换存储，但本地模式要继续零依赖可用。

## 决策

**迁移触发条件**

满足任意一条才迁移存储：需要多个问答实例、单用户可见文档数接近上限、任务中断造成实际影响、入库影响问答延迟、需要承诺 RPO / RTO、块数量超过 50 万。

**存储选型**

- 元数据、向量、关键词索引、任务队列统一使用 PostgreSQL 16 + pgvector。
- 每个索引版本对应一张 `chunks_v<n>` 表（维度随 Embedding 模型固定），切换与回退的模型保持不变。
- 权限过滤改为 JOIN `document_acl`，取消单用户可见文档数的上限。
- 关键词检索在 Postgres 上使用 jieba 预分词 + `simple` 配置的 tsvector，与阶段 3 的分词保持一致，不依赖数据库扩展。
- 原始文件使用 S3 兼容的对象存储，开启版本控制。

**数据访问层**

- repo 内部改用 SQLAlchemy Core（不使用 ORM），同时支持 SQLite 和 Postgres；函数签名不变。
- 迁移改用 Alembic，替代 `PRAGMA user_version`，按已有编号自动对接。
- 服务端模式下，迁移作为发布流水线中的独立步骤执行，不在应用启动时执行。
- 表结构变更遵循“先扩展、后收缩”。

**任务队列**

- 自建 `jobs` 表：幂等键部分唯一、租约与心跳、指数退避重试、`dead` 状态、协作式取消、进度。
- Postgres 用 `SKIP LOCKED` 领取任务，SQLite 用 `BEGIN IMMEDIATE`。
- 定时任务由 worker 用 advisory lock 选主后投递。
- 新增 `kb-studio-worker` 进程；本地模式下 worker 以线程形式运行在管理应用进程内。

**并发控制**

- 运行参数使用 `revision` + `If-Match`；文档使用 `row_version`。
- 切换索引使用条件更新。
- 同一文档的入库任务串行执行。
- 重建索引完成后，补写重建期间发生变化的文档。

**数据层权限隔离**

问答、管理、worker、迁移各用一个数据库账号，按最小权限授权；审计日志表只允许 INSERT 和 SELECT。

## 备选方案

- **Chroma 服务端 + Postgres**：权限只能用 ID 列表过滤，跨库写入需要对账，只作为过渡方案。
- **Milvus / Qdrant**：规模和性能更好，但权限必须写入向量元数据，与 ADR 0011 冲突，还要运维独立集群。块数量超过千万时再评估。
- **SQLAlchemy ORM**：与项目“不引入 ORM”的取向不符；Core 已经能解决方言差异。
- **Celery / Dramatiq + Redis**：多一个中间件，本地模式需要额外安装；当前任务量下收益不明显。
- **procrastinate**：基于 Postgres、成熟，但不支持 SQLite，本地模式还得另写一套。任务量增长后可以迁移过去。

## 影响

- 采纳并实施后，ADR 0001 的状态改为“已被 0014 取代”。本地模式仍然使用 SQLite + Chroma + 本地文件，作为 0014 中的一种存储实现。
- 迁移步骤 1–2（任务队列、数据访问层抽象）不依赖 Postgres，可以提前实施；本地模式因此获得“重启不中断任务”和并发控制。
- 已有数据通过 `kb-studio migrate-storage` 迁移：保留全部 ID，向量从 Chroma 直接复制，不重新调用 Embedding。
- **破坏性** 服务端模式需要先执行迁移命令再启动；`PUT /api/admin/settings` 需要携带 `If-Match`。
- 新增依赖：`sqlalchemy`、`alembic`、`psycopg`、`pgvector`；对象存储客户端按实施时的选择确定。
