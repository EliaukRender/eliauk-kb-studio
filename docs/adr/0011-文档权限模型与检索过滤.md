# 0011 文档权限模型与检索过滤

- 状态：提议中
- 日期：2026-10-23
- 涉及模块：`ingest` `db` `query` `eval` `api-public` `api-admin`
- 方案文档：[身份与权限](../方案/身份与权限.md)

## 背景

接入飞书后，知识库中会出现只对部分人可见的文档。问答端需要保证用户只能检索到自己在源系统中有权查看的内容，而且这种过滤不能只在前端做。现有的索引模型是“每个索引版本一个 collection、切回旧版本即回退”（ADR 0002）。如果权限跟着块存在各个 collection 里，就会和这种快照模型冲突。

## 决策

**主体与可见范围**

- 文档的可见范围是一个主体标识集合，可选值有 `tenant:*`、`user:<open_id>`、`dept:<id>`、`group:<id>`。
- 用户身份展开为另一个主体集合，其中部门要展开到全部上级部门。
- 两个集合有交集，文档即对该用户可见。
- 权限粒度是文档，存放在元数据库的 `document_acl` 表中。**不写入向量库**。

**默认拒绝**

- 可见范围为空的文档，任何人都不可见。
- 权限读取失败时，可见范围置空并标记错误，不沿用旧值。
- 外部协作者忽略。

**检索时过滤**

- 先在元数据库中算出用户可见的 `doc_id` 集合（排除已删除、已下线的文档），检索时作为预过滤条件传给向量库，阶段 3 的关键词检索同样适用。
- 检索结果再按集合做一次校验，作为纵深防御。
- 可见文档数为 0 时直接返回空结果。
- 单个用户可见文档数超过 `KB_ACL_INLINE_LIMIT`（默认 5000）时返回错误并告警，这是迁移存储的触发条件之一。

**强制经过访问范围**

- `query.search` 的 `AccessScope` 是必填参数，只能由 `identity.access` 构造，不提供公开的“全部可见”构造方式。
- import-linter 新增契约：`api.public`、`evaluation` 不得直接依赖 `rag`。

**权限变更**

- 权限变化与内容变化分开判断（`acl_hash` 与 `content_hash`）：权限变化不产生新版本，也不重新向量化。
- 权限刷新任务独立于内容同步调度，默认每 15 分钟一次。
- 提供“紧急下线”，立即对所有人隐藏文档。
- 所有权限相关的变化都会递增 `acl_epoch`，访问范围缓存随之失效。

**其他出口**

- `sources` 事件、`/api/status` 的文档数、回归测试、日志、阶段 4 的会话历史都按访问范围处理。
- 回归用例可以指定以哪些主体运行，用来编写权限回归用例。

## 备选方案

- **检索后过滤**：有权限的结果会被挤出 top_k，召回率随权限收窄而下降，排除。
- **把可见范围写入块元数据**（Chroma 1.5 支持数组和 `$contains`）：向量库原生过滤、规模大时性能更好。但权限变化要改写所有块；更严重的是旧索引快照保存的是旧权限，常规的“切回旧版本”操作就会让撤销的权限复活，排除。迁移到 Milvus 等独立向量库、规模远超上限时再重新评估。
- **每个权限组一个 collection**：组合爆炸，并且破坏一个索引版本对应一个 collection 的模型，排除。

## 影响

- 数据库迁移 2：新增 `document_acl` 表；`documents` 增加 `acl_hash`、`acl_status`、`blocked`；`data_sources` 增加 `default_acl`、`acl_refresh_interval_min`。已有文档迁移为 `tenant:*`，与现状一致。
- 不需要重建索引，向量库结构不变。
- 连接器新增可选能力 `fetch_acl`。阶段 1 的连接器接口不变，不提供该能力的来源使用数据源的默认可见范围。
- 迁移到 Postgres + pgvector 后，预过滤变为一次 SQL JOIN，过滤语义不变，单用户可见文档数的上限随之取消。
