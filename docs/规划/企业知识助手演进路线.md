# 企业知识助手演进路线

- 状态：规划中（未实施）
- 记录日期：2026-10-23
- 涉及模块：`ingest` `db` `auth` `query` `rag` `eval` `api-public` `api-admin` `web-chat` `web-admin` `server`
- 后续决策：每个阶段落地前，按本文「待定决策」一节新增对应 ADR

## 1. 背景

KB Studio 目前的定位是“本地优先的知识库问答客户端”：手动上传 `.md` / `.txt`，单个管理员维护，只监听本机。本文评估把项目演进为**企业内部知识助手**的可行性，并给出分阶段路线。

### 1.1 方向选择依据

2026 年知识库市场的调研结论如下。数据来自厂商公告和第三方估算，口径与时间点不统一，只用来看量级和趋势。

| 维度 | 头部类型 | 代表与量级 |
| --- | --- | --- |
| 需求最广 | 企业内部知识管理与搜索 | 约占企业 RAG 部署的 67%；Glean 2026 年 5 月 ARR 超过 $300M |
| 收入最高 | 智能客服知识库 | Zendesk AI 约 $200M ARR（2025 年底），Intercom Fin、Sierra 各超过 $100M；市场分散，头部份额不到 20% |
| 增长最快 | 法律等垂直行业 | Harvey 2026 年三季度 ARR 超过 $400M |
| 用户最多 | 个人知识库 | NotebookLM（已更名 Gemini Notebook）约 3000 万用户 |

另外两条与本项目直接相关的观察：

- 约 70% 的 RAG 系统没有评测体系。KB Studio 已有回归测试和索引蓝绿切换，这是现成的差异点。
- 技术趋势：混合检索已是生产基线，Agentic RAG（Agent 主动调用多个数据源并交叉核对）是当前最热的演进方向。

结论：企业内部知识助手是需求量最大、技术点覆盖最完整的方向，与项目现有能力的衔接也最顺。

## 2. 现状对照

| 企业知识助手需要的能力 | 现状 | 差距 |
| --- | --- | --- |
| 文档版本与增量更新 | 已具备：内容哈希、稳定块 ID、文档级回退 | 用文件名识别文档；接入外部数据源后要改成“源系统 + 源文档 ID” |
| 索引治理 | 已具备：索引版本、蓝绿切换、构建参数固化 | 基本够用 |
| 质量保障 | 已具备：回归用例 + 关键词判定 | 缺 LLM 打分、检索命中率指标、线上用户反馈 |
| 问答与引用 | 已具备：SSE 流式、来源、相关度分数 | 来源无法跳回源系统原文 |
| 多数据源接入 | 缺失：只能手动上传 `.md` / `.txt` | **核心缺口** |
| 用户身份与权限 | 缺失：问答端无鉴权，管理端为单管理员密码 + 暗门 | **核心缺口** |
| 检索质量 | 只有向量检索 + 阈值过滤 | 混合检索、Rerank、问题改写 |
| 多轮对话 | 缺失 | 会话历史、追问时改写问题 |
| 部署形态 | 只监听本机，SQLite + 本地 Chroma，进程内后台任务 | 多用户服务端：Postgres、任务队列、并发控制 |

已具备的数据分层、增量入库、索引版本与回归评测属于“知识库运维”能力，多数 demo 不具备，后续阶段都在这个基础上叠加，不需要推倒重来。

## 3. 演进路线

阶段按“每一步都能单独演示”的顺序排列。

### 阶段 1：数据源连接器（优先级最高）

> 方案：[多数据源接入](../方案/多数据源接入.md)；决策：[ADR 0009](../adr/0009-连接器抽象与文档身份规则.md)

目标：知识从“手动上传”变成“从企业文档平台同步”。

- 新增连接器抽象，统一接口为 `list_documents()`、`fetch(doc_id)`、`changed_since(ts)`；手动上传改为其中一种连接器。
- 第一个接入飞书文档（docx / wiki），完成 OAuth 授权和 docx 转 Markdown。
- 文档身份从 `filename` 改为 `(source_type, source_id)`，`documents` 表增加 `source_type`、`source_id`、`source_url`、`source_updated_at`。现有的哈希增量判断和版本表照常复用。
- 定时同步：先做轮询任务，后续再换成 webhook。
- 回答来源附带 `source_url`，可以跳回源系统原文。

改动集中在 `ingest/` 和 `db/`，问答链路不受影响。数据结构变更要兼容已有的 `data/`：已上传的文档迁移为 `source_type = upload`。

### 阶段 2：身份与权限

> 方案：[身份与权限](../方案/身份与权限.md)；决策：[ADR 0010](../adr/0010-用户身份与会话.md)、[ADR 0011](../adr/0011-文档权限模型与检索过滤.md)（提议中）。与本节的差异（已确认）：权限不写入块元数据，改为检索时按元数据库算出的可见文档集合预过滤，原因是块元数据中的权限会随旧索引快照“复活”

目标：不同用户只能检索到自己有权查看的内容。

- 问答端增加登录，优先使用飞书 OAuth，同时拿到用户身份和部门信息。
- 入库时把源文档的可见范围写入块元数据（如 `acl_users`、`acl_groups`、`space_id`），检索时按当前用户做元数据过滤。
- 管理端从“暗门 + 单密码”改为基于角色：管理员、知识管理员、普通用户。暗门可以作为本地模式的入口保留，但不再是唯一的安全边界。
- 问答端目前“只读、无鉴权”，契约要调整为“只读、需要鉴权”。`auth` 需要拆出问答端可依赖的只读身份校验部分，现有 import-linter 契约会受影响。

### 阶段 3：检索质量

> 方案：[检索质量](../方案/检索质量.md)；决策：[ADR 0012](../adr/0012-混合检索与重排序.md)（提议中）。与本节的差异（已确认）：检索指标（Recall@K 等）从阶段 4 提前到本阶段第一步，作为验收依据

目标：提高召回率和准确率，并能量化改进效果。

- 混合检索：BM25 + 向量，合并后排序。
- Rerank 精排。
- 问题改写：口语化问题、多轮追问先改写为独立的检索问题。
- 新链路全部放在 `query/` 中实现。问答端和回归测试共用这一层，改动天然被回归用例覆盖。

### 阶段 4：体验与质量闭环

> 方案：[对话与质量闭环](../方案/对话与质量闭环.md)；决策：[ADR 0013](../adr/0013-会话存储与质量闭环.md)、[ADR 0015](../adr/0015-会话服务与独立数据库.md)（提议中）；会话存储见[会话服务](../方案/会话服务.md)。与本节的差异：会话记录存放在独立的会话数据库中，由独立的会话服务读写，不使用 LangGraph Checkpointer（已确认）

- 多轮对话：结合 LangGraph Checkpointer 保存会话上下文。
- 用户反馈：回答支持点赞 / 点踩，差评问题可以一键转为回归用例。
- 评测升级：在关键词判定之外增加 LLM-as-judge 打分，以及检索层面的 Recall@K 指标。

### 阶段 5：Agentic 检索（可选）

> 暂不提前设计：工具集依赖阶段 2 的访问范围和阶段 3 的检索接口，效果评估依赖阶段 4 的评测体系，待前三者落地后再出方案

- 检索变成 Agent 的一个工具，再增加“查某个空间的最近更新”“按人或部门查文档”等工具。
- 由 Agent 决定检索哪些数据源、是否需要多步检索和交叉核对。

## 4. 部署形态的演进

> 方案：[服务端部署](../方案/服务端部署.md)；决策：[ADR 0014](../adr/0014-服务端存储与任务队列.md)（提议中），其中定义了迁移的触发条件

| 项 | 当前 | 企业化后 |
| --- | --- | --- |
| 监听地址 | 只监听 `127.0.0.1` | 服务端部署，配合鉴权和 HTTPS |
| 元数据库 | SQLite | Postgres（可用 pgvector 合并元数据与向量） |
| 向量库 | Chroma 本地持久化 | Chroma 服务端 / Postgres pgvector / Milvus |
| 后台任务 | FastAPI BackgroundTasks，重启会中断 | 可重试的任务队列，入库 Worker 独立部署 |
| 会话 token | 后端内存 | 持久化会话或标准 OAuth / OIDC |
| 并发 | 不处理并发操作 | 需要锁或乐观并发控制 |

存储迁移分两步：先保留 SQLite + Chroma 完成阶段 1、2 的功能，等到需要多用户、多进程时再迁移。repo 层已经隔离了数据库访问，迁移成本可控。

## 5. 风险与注意事项

- **数据合规**：接入真实企业文档后，Embedding 和问答会把文档内容发送给百炼和 DeepSeek。使用公司文档前要确认是否允许外发；不允许时改用本地 Embedding 和本地模型。演示阶段使用测试空间和虚构的公司制度文档。
- **权限泄露**：权限过滤必须在检索层执行，不能只在前端隐藏。源文档权限变化后，块元数据要随同步更新。
- **定位冲突**：README、架构设计、ADR 0001 / 0004 / 0007 都以“本地单人使用”为前提。进入阶段 2 前，要先更新项目定位，并用新 ADR 替代或修订相关决策。
- **范围控制**：每个阶段独立交付、独立验收。不要在阶段 1 顺带引入权限或迁移数据库。
