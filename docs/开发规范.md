# 开发规范

本文是项目的硬性约束，人工开发与 AI 辅助开发同样适用。能自动检查的规则都已接入 `scripts/check.sh`，不能自动检查的规则依靠评审。

## 环境

| 工具 | 版本 |
| --- | --- |
| Python | 3.12+，由 uv 管理（`backend/.python-version`） |
| Node | 22+ |
| pnpm | 11（见 `frontend/package.json` 的 `packageManager`） |

npm 源在 `frontend/.npmrc` 中固定为 `https://registry.npmmirror.com`。

## 边界与分层

项目按“可以随时拆成独立部署的两个系统”来组织，见 [ADR 0007](./adr/0007-应用边界与可拆分部署.md)。

### 两个应用

| | 问答应用 | 管理应用 |
| --- | --- | --- |
| 面向 | 使用者 | 知识库运营、管理员 |
| 后端 | `apps/chat_app.py` + `api/public/` | `apps/admin_app.py` + `api/admin/` |
| 前端 | `index.html` + `src/apps/chat/` | `admin.html` + `src/apps/admin/` |
| 默认端口 | 8765 | 8766 |
| 能力 | 只读：检索、问答、状态 | 读写：文档、索引、评估、设置、鉴权 |

两个应用之间**只能通过 URL 跳转**（`shared/config/app-links.ts`），不能共享路由、状态或互相引用代码。

### 后端分层

```
cli → apps → api → ingest | auth → evaluation → query → rag | db | storage → settings
```

- 只允许上层依赖下层。同一层用 `|` 分隔的模块互相独立。
- 问答端（`api.public`、`apps.chat_app`）只能经由 `query` 访问知识库，**直接或间接**依赖 `api.admin`、`auth`、`ingest`、`evaluation`、`storage` 都会被 import-linter 拦截。
- 规则定义在 `backend/pyproject.toml` 的 `[tool.importlinter]`，修改契约必须同时新增或更新 ADR。

### 前端边界

| 目录 | 可以依赖 | 禁止依赖 |
| --- | --- | --- |
| `src/apps/chat/` | 自身、`src/shared/` | `src/apps/admin/` |
| `src/apps/admin/` | 自身、`src/shared/` | `src/apps/chat/` |
| `src/shared/` | 自身、第三方库 | 任何 `src/apps/` |

- 跨目录引用必须使用 `@/` 别名，禁止 `../`。同目录及子目录可以用 `./`。
- 共享层不感知鉴权：HTTP 客户端由 `createHttpClient` 创建，token 与 401 处理由使用方注入。
- 以上规则由 ESLint `no-restricted-imports` 检查（`frontend/eslint.config.ts` 的 `boundary/*` 配置）。

### 新功能放在哪里

| 需求 | 位置 |
| --- | --- |
| 问答页的新交互 | `frontend/src/apps/chat/` |
| 后台新页面或新操作 | `frontend/src/apps/admin/views/<页面>/` |
| 两个应用都要用的组件、工具、类型 | `frontend/src/shared/`，确认它不依赖任何应用的业务逻辑 |
| 新的只读查询能力（问答端要用） | `backend/src/kb_studio/query/` |
| 改变知识库内容的操作 | `backend/src/kb_studio/ingest/`，接口放 `api/admin/` |
| 新的模型、切分、向量库能力 | `backend/src/kb_studio/rag/` |
| 新表或新字段 | `backend/src/kb_studio/db/`，同时编写迁移逻辑，见下文「数据与配置」 |

不确定放在哪里时，先按“它是否改变知识库内容”判断：会改变的属于管理侧。

## 模块化

- **单文件行数上限**：业务代码 250 行、测试 400 行（不计空行和注释）。前端由 ESLint `max-lines` 检查，后端由 `scripts/check_py_size.py` 检查。超出时按职责拆分，不要靠压缩格式规避。
- 页面过大时，把分区拆到同级的 `components/` 目录；后端模块过大时，拆成同名子包。
- `types` 只放类型，运行时常量放 `constants/`。

## 命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 前端目录 | kebab-case | `apps/admin/views/documents/` |
| Vue 组件 | PascalCase | `UploadPanel.vue` |
| 页面组件 | `XxxView.vue` | `IndexesView.vue` |
| 其他 TS 文件 | kebab-case | `http-client.ts` |
| 组合式函数 | `useXxx` | `useChatStream.ts` |
| Pinia store | `useXxxStore`，文件名为领域名 | `stores/session.ts` → `useAdminSessionStore` |
| Python 模块 / 函数 | snake_case | `index_state.py`、`ensure_current_index` |
| 文档 | 中文文件名 | `docs/开发规范.md` |

## TypeScript / Vue

- 使用 `<script setup lang="ts">` 和 Composition API。
- 类型声明用 `type`，不用 `interface`（`.d.ts` 的模块扩充除外）；不使用 `enum`，改用 `as const` 对象加派生类型。
- 类型导入使用 inline 写法：`import { type Foo, bar } from '...'`。导入顺序由 `simple-import-sort` 整理。
- naive-ui 组件（`n-*`）和图标（`i-ri-*`）由 unplugin 自动注册，模板中保持 kebab-case。
- 业务代码不直接使用 axios，通过各应用的 `api/` 封装调用。
- 颜色使用语义 token（`bg-surface`、`text-muted`、`border-line`、`text-primary`），不写死色值。

## Python

- 格式与静态检查使用 ruff（行宽 120），配置在 `backend/pyproject.toml`。
- 接口错误统一抛 `HTTPException`，`detail` 用中文，前端可以直接展示。
- 同步接口里可以调用阻塞的网络请求（FastAPI 会放进线程池执行）；`async` 接口里禁止调用阻塞代码。
- 后台任务失败时必须把错误写回对应记录（如 `index_versions.error`），不能只打日志。
- 捕获宽泛异常时用 `# noqa: BLE001` 加上理由说明。

## 数据与配置

- **部署相关配置一律走环境变量**（`settings.py` 中的 `KB_*`），不能在代码里写死主机、端口或路径。新增配置项时，同步更新 `README.md` 和 `docs/架构设计.md` 中的配置列表。
- **密钥只放在 `backend/.env`**，该文件已加入 gitignore；新增密钥时同步更新 `backend/.env.example`。代码、文档和提交信息里都不能出现密钥值。
- **数据结构变更必须兼容已有数据**：新增字段要有默认值，或者在 `db/connection.py` 的初始化中补迁移。不能要求用户删除 `data/`。
- 改变切分规则、块元数据或 Embedding 调用方式时，必须在 CHANGELOG 中注明“需要重建索引”。
- 分进程部署时必须使用 Chroma 服务端（`KB_CHROMA_URL`），不能让多个进程共享本地 PersistentClient。

## 测试

| 层 | 工具 | 位置 |
| --- | --- | --- |
| 后端 | pytest | `backend/tests/` |
| 前端 | Vitest + happy-dom + @vue/test-utils | `frontend/tests/unit/`，目录结构与 `src/` 对应 |

- **必须覆盖**：纯逻辑模块，比如判定规则、哈希与版本决策、切分与块 ID、鉴权、SSE 解析、暗门触发。
- **不强制覆盖**：页面布局、纯展示组件、依赖外部模型 API 的链路。后者用回归测试用例验证。
- 单元测试不能调用真实的模型 API，也不能读写用户的 `data/` 目录。

## Git 工作流

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 已发布版本 | 只接受从 `develop` 合并的发版提交，每次合并后打 tag `vX.Y.Z`；**禁止直接在 main 上开发或提交** |
| `develop` | 日常开发集成 | 默认工作分支，所有开发在这里进行 |
| `feature/<主题>` | 较大或试验性的改动（可选） | 从 `develop` 拉出，完成后合并回 `develop` 并删除 |

- 提交格式：`type(模块标签): 中文描述`，模块标签见 [变更管理](./变更管理.md#模块标签)。
- 一次提交只做一件事，提交前 `scripts/check.sh` 必须通过。
- 发版：在 `develop` 上整理 CHANGELOG 并更新版本号，然后 `git merge --no-ff develop` 到 `main`，再打 tag，详见 [变更管理](./变更管理.md#发版流程)。

## 完成标准

一项开发任务只有同时满足以下条件才算完成：

1. `scripts/check.sh` 全部通过。
2. 涉及的行为有对应的单元测试，或者在回归用例中有覆盖。
3. CHANGELOG「未发布」下已追加条目，并标注模块标签。
4. 架构有变化时，`docs/架构设计.md` 已同步；属于重大决策的，已新增 ADR。
5. 新增的配置项、密钥、启动方式已写进 README。
